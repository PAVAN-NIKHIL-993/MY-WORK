That statement is **partly true, but often oversimplified**. Humans do enjoy turning every bug into a religion.

### What's actually happening?

On ESP32, the Arduino `String` class dynamically allocates memory from the heap whenever it needs to:

- Grow
- Concatenate (`+=`)
- Create temporary strings
- Return strings from functions

Example:

```cpp
String msg;

void loop() {
    msg += "Temperature: ";
    msg += String(random(100));
}
```

Over hours or days, repeated allocations and deallocations can leave the heap looking like Swiss cheese:

```
[free][used][free][used][free][used]
```

You may still have plenty of free RAM, but not enough **contiguous** RAM for a new allocation.

Result:

- Random crashes
- Guru Meditation errors
- Reboots
- Failed allocations
- WiFi instability

---

## Why char[] helps

A fixed buffer is allocated once.

```cpp
char msg[64];

snprintf(msg, sizeof(msg),
         "Temperature: %d",
         random(100));
```

Memory layout:

```
Stack:
[msg buffer]
```

No heap allocation.

No fragmentation.

No surprises at 3 AM when the device has been running for a week and decides existence is optional.

---

## But String isn't always evil

ESP32 has:

- Much more RAM than AVR Arduinos
- Better heap management
- Multiple heap regions

This works perfectly fine:

```cpp
String deviceName = "WeatherStation";
```

because allocation happens once.

Even this is usually fine:

```cpp
String msg = "Temp: " + String(temp);
```

if done occasionally.

The real danger is:

```cpp
String log;

while(true)
{
    log += newData;
}
```

or

```cpp
String html;
html += "...";
html += "...";
html += "...";
```

thousands of times.

---

## Better fixes if you want to keep String

Reserve memory upfront:

```cpp
String buffer;

void setup()
{
    buffer.reserve(512);
}
```

Now String allocates once and reuses the memory.

This dramatically reduces fragmentation.

---

## How to prove fragmentation

Monitor heap:

```cpp
Serial.printf("Free Heap: %u\n",
              ESP.getFreeHeap());

Serial.printf("Largest Block: %u\n",
              ESP.getMaxAllocHeap());
```

If:

```
Free Heap = 120000
Largest Block = 4000
```

you have fragmentation.

Lots of memory exists, but it's scattered into tiny pieces.

## Professional ESP32 firmware practice

For systems expected to run:

- weeks
- months
- years

Engineers generally prefer:

```cpp
char buffers[]
snprintf()
static buffers
fixed-size queues
```

for frequently executed code.

Use `String` for:

- configuration
- setup code
- debugging
- occasional text manipulation

Avoid `String` in:

- high-frequency loops
- networking buffers
- telemetry streams
- web servers handling many requests
- long-uptime industrial devices

### Practical rule

If your ESP32 crashes after several hours or days and you're heavily using `String`, it is one of the first things worth investigating. Replacing dynamic string building with fixed `char[]` buffers and `snprintf()` often eliminates heap fragmentation issues, but it's not the only possible cause. Memory leaks, stack overflows, watchdog resets, Wi-Fi bugs, and buffer overruns can produce very similar symptoms.

The heap is a bit like a workshop floor. A few tools lying around are fine. Spend six months throwing tools everywhere and eventually someone trips over a screwdriver. In embedded systems, that someone is usually your firmware.
